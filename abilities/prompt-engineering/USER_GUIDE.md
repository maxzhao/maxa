# Prompt Engineering 用户指南

这个 Ability 用于创建、维护、优化或修正提示词、系统提示词、Agent 指令、任务说明和提示词模板。

## 可以这样提出需求

- “帮我从零写一个用于代码审查 Agent 的 system prompt。”
- “优化这个提示词，让输出更稳定并返回结构化 JSON。”
- “检查这个 prompt 有没有冲突、过度约束或不清晰的地方。”
- “把这段普通需求改成可交给子代理执行的任务提示词。”
- “维护已有 system prompt，不要大改，只做最小 patch。”
- “这个 Agent 总是不运行测试，帮我修正它的指令。”
- “为这个提示词设计 few-shot 示例和边界用例。”
- “帮我把提示词模板变量、输入、输出格式整理清楚。”
- “根据失败输出修正 prompt，并说明哪些规则该保留、哪些该删。”
- “用提示词质量清单审查这组 prompt 文档是否合格。”
- “根据你已有的知识，用准确术语替代提示词中的通用教学，逐句清理，但保留当前行为要求、环境差异和安全约束。”
- “解释这个提示词规范参考了哪些资料，哪些常见技巧没有采纳。”

## 自主执行、审批和完成边界

适合处理 Agent 过早停工、反复确认、工具失败后立即转人工、通知后不再继续，或验收通过后仍不断自检的问题。

示例：

- “区分这个提示词中的内部核实、信息澄清、真正审批和普通通知，不要把所有‘确认’都变成询问用户。”
- “工具重试失败但还有安全替代路径时，让 Agent 继续解决；保留权限和安全限制。”
- “部署仍需批准，但允许先完成已授权、可逆的准备工作。”
- “已有相关上下文时不要每次读完整仓库；必要信息过期时也不要禁止恢复。”
- “验收通过且没有未解决疑点时直接完成，不预设评分、不合格结论或返工轮次。”

Agent 只在相关行为需要设计或修复时加载专项说明。不会因为模型更强就删除安全边界、必要审批或团队要求的验证。

## 去重、迁移和模型建议采纳

示例：

- “合并主提示词和注入片段中的重复协议，保留一个权威来源。”
- “把低频流程移到按需文档，但检查它是否仍在首次相关动作前加载，安全要求是否保持原有权威。”
- “不要只改示例，也检查实际加载的角色文件、模板和生成提示词。”
- “评估这份模型最佳实践是否适合当前宿主，不要直接套用其他工具的描述截断阈值。”

职责分工：本技能处理指令语义；技能描述、触发与资源布局交给 `ability-creator`。普通编辑不会被要求重新联网研究或执行全部行为样例。

## 适合提供的材料

可直接提供：现有 prompt、目标模型、调用位置、失败输出、期望输出格式、示例输入、项目约束、评估方式、上线风险，或要审查的目录/文件列表。材料越接近真实运行场景，优化结果越可靠。

## 常见输出

- 新提示词或最小修改 patch。
- 设计理由和保留/删除的规则。
- 验证建议或代表性测试样例。
- 可复用模板结构。
- 对提示词规范、模板或审查结论的来源取舍说明。
- 分层验证结果：静态合同检查、实际工具集成和模型行为试验分别说明。lint 或生成提示词通过，不等于已证明减少停顿或提高完成率。
