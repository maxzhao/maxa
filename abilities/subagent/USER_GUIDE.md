# subagent 用户指南

本能力用于让 Agent 判断、配置和使用 SubAgent：无工具问答、独立子代理、fork 当前上下文、恢复 `save_id`、并行子代理、多专家讨论、工具限制、模型档位、历史查询、排障与流程文档固化。一次 `load(target="subagent")` 同时获得使用指导、参考文档和 MCP 工具，无需分别加载指导包与服务。你只需说明目标、上下文来源、是否需要独立/并行/续跑、输出格式和限制。

## 旧入口迁移

`subagent-admin` 已直接重命名为 `subagent`，不保留兼容入口；现行工具地址 `@subagent:run_agent` 等不变。已有会话如果仍加载旧包，需先清理该会话的旧 Ability 加载上下文，再加载 `subagent`；仅重启 Neovim 后恢复原历史不一定能清除旧加载记录。本次不批量改写历史会话。

## 快速说法

- “这个问题适合开子代理吗？先判断。”
- “让另一个 LLM 不调用工具，给我第二意见。”
- “fork 当前上下文，从安全角度审查。”
- “开独立子代理读取这些文件，做可维护性审查。”
- “基于 save_id `<id>` 继续剩余分析。”
- “先创建一个上下文准备会话，加载必要技能、MCP 和文档，后续子代理都从这个 save_id 派生。”
- “并行三个子代理：性能、安全、可维护性；最后合并结论。”
- “组织 multi_agent 多专家讨论这个架构方案。”
- “限制子代理只读文件，不要改代码。”
- “把这套多代理执行流程固化成可复用指导文档。”
- “合理使用子代理：主会话保留主干，默认串行，每次完成后验收；同领域优先恢复，已有工作适合迁移时，要求原子会话交接到同父的新子会话。”

## 默认：合理使用子代理

当你说“请合理使用子代理”时，Agent 应默认执行以下策略：

1. 主 Agent负责架构、跨模块主线、连续调试、最终集成和完整验证。
2. 只委派独立、边界明确、可以单独验证的工作，例如只读审查、Schema/migration、纯 reducer、类型合同或独立测试。
3. 一项内聚的工程变更默认只建立一个长期实施子会话。即使工作依次跨越 Schema、Service、Workflow、UI、测试与修复，只要共享规格、接口或工作树，就优先恢复同一个 `save_id`，不能按目录或阶段新开会话。
4. 不仅每次恢复前要检查；首次子会话建立后，任何新的相关 `run_agent` 之前也必须先检查已有 `save_id` 和最新 `context_status`。同时根据连续性收益、剩余容量和下一任务规模决定：
   - 容量充足：继续恢复；
   - 只够小修：标记为仅小型跟进；
   - 容量不足且已有工作/上下文适合迁移：通过 `resume_agent.goal_prompt` 明确要求原子会话进行一次交接；原调用继续等待同父接替者的最终结果。
5. 只有不存在相关会话、原会话无法执行交接，或任务真正独立且文件范围不重叠时，才新建 `run_agent`。Token 比例高本身不授权子代理自行交接；从 Schema 转到 Service、Workflow、UI、测试或修复本身不是理由。
6. `resume_mode="new_chat"` 和 `fork_agent` 都会继承历史，不是节省上下文的方法。
7. 实现工作默认串行：等待一个子代理完整结束，主 Agent检查实际 diff、越界情况和验证结果后，优先恢复同一个会话推进相关下一步。
8. 仅当接口已经冻结、任务真正独立且文件范围不重叠时才并行。同一主 Chat 的整个委派树最多同时运行 **5 个子代理**，嵌套共用额度；正在协调或等待后代的子代理也占一个名额。子代理获得明确的剩余额度后才可继续委派。
9. 子代理报告不是完成证据；最终结论必须由主 Agent复核。
10. 初审和复审尽量恢复同一个 Reviewer 会话；容量不足时再用紧凑 findings handoff 更换 Reviewer。

示例：

- “合理使用子代理完成这个重构。默认只开一个实施会话，后续 Schema、Service、UI、测试和修复都优先 resume；不要把连续实现链拆成很多新会话。”
- “继续使用 Schema 子代理前先检查上下文和已完成工作；适合迁移时，resume 原会话并明确要求一次交接，保留稳定结论、路径和当前错误。”
- “恢复之前的 Reviewer 做复审；容量不足但能整理 findings 时，要求它交接到同父的新 Reviewer 子会话。”

子会话自动收尾预算耗尽时，已有 Telegram／Chat 决策中也可选择“交接到新会话继续”。它仍是子代理交接，不会升为主会话或结束父工具等待；每次交接都需要新的明确指令。

## 场景 1：无工具第二意见

适合摘要、改写、方案风险、轻量推理。

示例：

- “让另一个 LLM 用三句话总结这个方案的风险，不用工具。”
- “快速给第二意见：这个 API 设计哪里可能有问题？”
- “改写这段说明，保持简洁。”
- “只做文本推理，不读文件不执行命令。”

## 场景 2：fork 当前完整上下文

适合子代理必须知道当前会话全部背景、代码片段、决策和约束。fork 不会减少上下文；是否压缩由独立的授权协议决定。未获压缩授权时，Agent 可以继续主会话工作或选择可容纳的有限委派，不会仅因不能压缩而要求你批准或停工。

示例：

- “fork 当前上下文，让子代理检查方案遗漏。”
- “基于刚才讨论的实现，专门分析边界条件。”
- “继承当前对话，从测试策略角度复核。”
- “检查我刚才的修复思路是否会引入回归。”

## 场景 3：独立子代理调查

适合只给定目标和资料来源，不需要完整聊天历史。

示例：

- “开独立子代理，只读取 `src/auth/`，审查认证逻辑。”
- “读取这几个文件，输出潜在 bug 和修复建议。”
- “阅读这个 URL 的文档，总结对我们实现的影响。”
- “分析这张截图的 UI 问题，不需要工具访问。”
- “结合 `.maxa/knowledge/sources/rules/security.md` 做安全审查。”

## 场景 4：inherit、独立与 fork

- 需要完整消息历史：说“fork 当前上下文”。
- 不要带入聊天历史，只继承当前工具/规则/模型：说“开独立子代理，读取这些资料”。
- 任务完全独立：说“不要带入前面对话”。

## 场景 5：指定角色或专家视角

示例：

- “让子代理作为安全工程师审查 OWASP Top 10 风险。”
- “用架构师视角分析边界和演进风险。”
- “让性能工程师只关注热点路径和缓存策略。”
- “使用 agency 里的工程安全角色审查认证模块。”
- “自定义角色：严格代码审查员，只输出高价值问题。”

## 场景 6：prompt-cache warmup 调试

这是调试/验证场景，不是常规用法。仅当你明确要测试 fresh-prefix 子会话缓存时使用；仅支持 `run_agent`，不支持 `fork_agent`、`resume_agent`、`multi_agent`。

示例：

- “这次 run_agent 强制 warmup，验证 cache 文件。”
- “这次不要 warmup，对比无缓存行为。”
- “验证 subagent warmup=force 是否生成 `.maxa/history/caches/` 文件。”

## 场景 7：继续历史或使用 save_id

`save_id` 是相关任务的默认后续入口，不只是中断恢复工具。一个实施子代理完成首个切片后，后续集成、修复、验证应先恢复它。恢复前，Agent应判断领域连续性、剩余上下文和已有工作是否适合迁移；适合时，通过恢复消息要求一次子会话交接，并把最终返回的接替者 `save_id` 作为后续入口。只有原会话无法执行交接或任务真正独立时，才直接新建子代理。

示例：

- “用 save_id `<id>` 继续上次调研，并总结剩余工作。”
- “基于这个 save_id 完成未做完的验证。”
- “恢复历史会话，结合新需求重新评估方案。”
- “并行恢复两个 save_id，比较结论并合并建议。”
- “查询子代理返回的 save_id 摘要，决定是否继续。”

## 场景 8：上下文准备会话

适合先建立一个“已加载必要知识/技能/MCP/路径约束”的基础子会话，拿到 `save_id` 后，再让多个后续子代理从这个基础上下文派生执行具体任务。

使用边界：

- 主代理先通过 `messages.tool_call` 加载已知必要能力及专项指导，并传递规则、文档、图片/目录入口；基础会话只补充具体缺失项，并验证关键路径。
- 基础会话不解决下游任务、不生成产物、不改文件、不写完整项目计划。
- 后续具体任务应基于基础 `save_id` 派生新会话；不要让每个子代理从零加载全部资料。

示例：

- “先创建上下文准备会话：加载设计规范、genai 技能和参考图目录，只返回 READY 和 save_id。”
- “建立基础上下文：读取这些规则文档并验证输出目录，后续多个子代理从它派生。”
- “基于刚才的上下文准备 save_id，新开三个任务会话分别做组件板、状态板和响应式板。”
- “这个基础会话不要做计划，不要生成图片；只加载上下文并确认缺失项。”

注意：如果要从基础 `save_id` 派生多个并行任务，Agent 应使用恢复历史的新会话分支，而不是重新开普通独立子代理。

## 场景 9：并行多视角分析

适合子问题互相独立，或需要保留多个视角。整个委派树并行上限为 **5**；例如一个子代理负责协调时，其全部后代合计最多同时运行 4 个。异步提交成功不代表释放名额，Agent 会等待实际完成或确认取消清理后再启动下一批。普通工具批处理不受这项子代理上限影响。

示例：

- “并行分析同一方案：性能、安全、可维护性，最后合并优先级。”
- “分别评估三个候选方案，推荐最佳方案。”
- “并行两个 fork：一个找漏洞，一个找测试缺口。”
- “一个恢复历史 A，一个恢复历史 B，最后合并差异。”
- “这些结果都重要，请逐个返回结论、证据和 save_id。”

## 场景 10：multi_agent 多专家讨论

适合多个角色讨论、辩论、交接，最后由 final agent 输出结论或执行方案。Agent 会先使用 `agency-nexus`。

示例：

- “用多专家讨论这个架构方案，最后给落地建议。”
- “组织安全、性能、产品三个角色讨论是否值得做。”
- “专家团队先讨论风险，再由 final agent 输出实施计划。”
- “用 agency 角色库做一次 NEXUS 编排讨论。”

## 场景 11：上下文资料

你可以直接说子代理应该看什么：所需能力、能力专项指导、项目规则/规格、文件、目录、URL、图片和已确认的决策。主代理应准备这项子任务所需的完整上下文，而不是只给一句目标、假定子代理知道父会话背景，或加载所有无关资料。

主代理可以通过 `messages` 中的 `tool_call` 执行真实 `load`：先加载所需 Ability，再加载它的相关 reference。加载 Ability 根入口不等于读过全部参考文档。前置调用在目标子会话执行、由运行时补全调用/结果，按序完成后才开始目标；工具限制、授权和失败停止规则仍然有效。

可以这样说：

- “创建只读 MCP 调查子代理，先通过 tool_call 加载 mcp-creator 和 Native Server 指导，再传入范围、已确认接口与交付要求。”
- “恢复现有子代理，保留已加载能力，只补充这次新增的接口契约指导，不重复前次操作。”
- “两位讨论代理都需要同一能力和规范，请放入共享 messages，只加载一次，再共享完整结果。”

URL context 只提供链接引用，不自动获取正文；需要正文时明确使用网页能力。fork 已继承历史，不重复传递；resume 先检查容量及已有内容，只补缺失/变化项。

示例：

- “读取 `src/api/` 和 `src/db/schema.ts`，检查接口与数据模型是否一致。”
- “把这个文档 URL 作为上下文，总结迁移步骤。”
- “结合项目安全规则做审查。”
- “给子代理这张截图，只描述 UI 问题。”
- “资料已在当前会话里，fork 时不要重复传。”

## 场景 12：模型档位

默认继承当前或历史会话模型配置。明确要切换时再说：

- “用 fast 快速判断。”
- “用 powerful 深度推理。”
- “用 coding 分析代码。”
- “用 creative 生成创意方案。”
- “不要切换模型，继承当前配置。”

## 场景 13：工具限制与安全边界

示例：

- “限制子代理只能读文件，不能写。”
- “可以读文件和跑测试，但不要改代码。”
- “不要访问任何工具，只做文本分析。”
- “只允许 Chat builtins 的读文件和执行命令能力。”
- “输出建议，不要实际修改项目。”

## 场景 14：窗口、打断和取消

示例：

- “子代理卡住时怎么打断？”
- “说明 Ctrl+C 和 q 的区别。”
- “子代理窗口没关闭，帮我排查。”
- “判断无响应是模型、工具还是窗口管理问题。”

## 场景 15：token、压缩和历史查询

示例：

- “如果子代理 token 超限，请先压缩再继续。”
- “完成后记下 save_id，方便后续继续。”
- “查询这个 save_id 的摘要。”
- “基于刚才子代理历史继续下一步。”
- “如果 fork 因上下文太长失败，说明恢复方案。”

## 场景 16：固化多代理流程文档

适合把主代理监督、执行代理推进、修复代理处理局部 RED、探索代理扩展风险等流程写成可复用规范。

示例：

- “把刚才这套多代理执行流程固化成指导文档。”
- “写一份可复用 SubAgent 工作流文档，不要写任务日志。”
- “流程涉及主代理、执行代理和修复代理，整理成可导航规范。”
- “检查这份多代理流程文档，摘要是否写清谁接着谁做。”

## 场景 17：维护 SubAgent 实现

示例：

- “排查 fork_agent 失败，按 SubAgent 架构查入口。”
- “SubAgent 工具不可用，检查 tool_registry 继承逻辑。”
- “run_agent 的 inherit 推断不符合预期，定位相关代码。”
- “multi_agent 没结束，检查 coordinator 和 handoff 流程。”
- “子代理越界执行父任务，检查边界标记和消息结构。”
- “新增 adapter 预设，找到应改位置。”

## 场景 18：明确交接当前主会话

当你明确要求“把当前主会话交接给新的主会话继续”时，Agent可以使用 `run_agent` 的 `handoff` 模式。它先将必要决策、进度、错误和验证状态写入 `.maxa/drafts/`，用文件消息传给新会话；准备成功并安全结算当前工具后关闭旧 Chat，新主 Chat直接继续工作并向你交付，不等待子代理返回。

只有主会话可以发起；子会话尝试会明确报错，不会自动升级。高 token、工作复杂或一般“继续”都不会自动触发交接；这次交接也不会授权下一次。准备失败保留旧会话，旧历史不会删除。

示例：“请将当前主会话交接给新的主会话继续。把必要状态分文件写入草稿，通过文件消息传递，保持目标和已确认决策。”

## 监督者子代理说法

如果希望子代理在自己的会话中监督执行代理、修复代理或复核代理，请明确职责边界：

- “请让子代理作为监督者执行该任务。它可以创建执行代理或修复代理，但不得把我的请求原样递归转包；每层代理必须有清晰职责、停止条件和结果回传方式。”
- “当前主代理负责整体实现和集成，只把独立的 API 调查交给一个可恢复的子代理；后续相关复核继续使用同一个会话。”

## 使用建议

- 说明目标、上下文来源、输出格式和限制。
- 简单任务让主 Agent 直接做。
- 一项内聚工程变更默认只建立一个实施子会话，后续相关阶段优先 `resume_agent`。
- 继续历史时提供 `save_id`；未显式提供时，Agent也应跟踪本任务已返回的 `save_id`。
- 只有确实需要复用共同背景并派生后续任务时才创建上下文准备会话；普通子任务直接通过 `messages` 传递必要上下文，不额外创建准备会话。
- 多代理协作时说明视角/角色和合并方式。
- 风险限制用“只读”“不改代码”“不执行命令”或列出允许能力。
- 维护 SubAgent 本身时说明故障现象；Agent 会按架构、消息结构、继承、窗口、token 和 multi-agent 流程排查。
