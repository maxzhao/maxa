# Spec Admin 用户指南

Spec Admin 管理可验证的行为规格：需求边界、Proposal、Delta Spec、稳定规格、覆盖审计和验收收敛。制定规格与规划实施分开：规格写入不需要任务，TaskAdmin 用于规划尚未执行的实施工作。

## 创建或修改规格

示例：

- “为这个功能创建一份可验证的行为 spec。”
- “这个现有行为要改，先创建 proposal 和 delta spec。”
- “不要直接覆盖稳定规格，先建立可审核的 change。”

讨论、编写、修改或接受规格不自动创建任务，也不自动开始开发。未定问题保留在规格中；不把“编写规格”包装成 implementation 任务。新草案、proposal 和 delta 不要求任务字段，正式规格保持独立。纯错字或明确的普通链接修正可直接完成，不创建 proposal/delta，也不改变行为、规则身份、证据或生命周期。

## 面向 LLM 的规格优化

规格面向独立 LLM 阅读：以尽量少的 token 完整表达行为契约。根据内容选择具名条款、共享前提、条件表或有序状态转换；保留权限、时序、失败、限值、例外和已知缺口。规则身份、有效引用和下游所需格式保持可用。

示例请求：

- “优化当前正式规格，保留完整语义，报告全部文件的 token 变化与验证结果。”
- “把这份规格重组为便于 LLM 独立理解的紧凑契约，保留公共锚点和精确接口。”
- “精简这组规格，并用只读取新版的独立读者验证关键边界。”
- “下游使用 OpenSpec 校验器，请保持兼容格式并优化正文密度。”

批量优化不创建任务。Agent 先把每份规格完整读至 EOF，再从全部行为事实重建整篇文档并完整替换；随后按行为组核对原文与新版，使用同一 tokenizer 统计完整文件。已足够紧凑的文件可保留并说明原因；目标清单、逐文件结果和验证直接交付，必要维护结果写入现有规格日志。原有实现任务与验证状态保持真实。

## Change workspace

新 change 只包含：

```text
proposal.md
specs/<capability>/spec.md
```

SpecAdmin 不创建 `design.md` 或 `tasks.md`：

- 用户要求规划实施时，技术方案写入实施任务的 `plan.md`；
- 执行既有实施任务时，`todo.md` 保存必要的进度、验证、阻塞和下一步，不作为规格编写日志。

## 只读分析和审查

示例：

- “检查这份 spec 是否有歧义，不要修改文件。”
- “检查实现是否符合稳定规格。”
- “找出 spec、实现和验证之间的不一致。”

解释、分析、review、convergence assessment 及授权的规格修正均不因记录结果而创建任务。默认只检查你指定的变更及直接影响，不把检查维度当成全面审计清单；范围外发现只报告。需要实施修复时，才按请求规划未完成的工作。

## 与 TaskAdmin 配合

示例：

- “根据这份规格规划尚未开始的 P1 实施，创建完整实施任务。”
- “继续这个 spec-driven 任务，从 TaskAdmin TODO 推进实现。”
- “检查 proposal、delta、实现、任务 TODO 和验证是否收敛。”
- “实现和验证已完成，请合并稳定规格并完成 change lifecycle。”

任务面向未来实施，不用于补记已完成的规格编写、审查或提升。实施 plan 引用精确规格路径和范围，不复制规格正文；内聚实施保持一个任务，独立交付物才按需拆分。历史任务引用同一规格不代表可复用；旧临时任务字段只是恢复线索，须核对实施计划。普通代码开发不会仅因使用 TaskAdmin 就自动升级为规格工作流。

## 从代码提炼规格

示例：

- “从这个旧模块提炼 draft behavior spec。”
- “按入口、权限、状态变化、失败路径和验证方式做覆盖审计。”
- “只做证据和缺口分析，不写文件。”

证据分析和保存 draft spec 都不创建任务。用户要求规划后续实现或行为修复时，才创建面向未完成工作的实施任务。单一行为的提取不会自动扩成整个模块或仓库审计；按实际检查边界交付，并保留已知缺口。

## 验收、提升与清理

规格只要求覆盖本次行为的最小充分证据，具体方法由 TaskAdmin 的验证规则决定。UI 展示和交互使用实际应用中的操作与观察，不通过编写单元/组件/E2E 测试、mock 或临时诊断脚本替代；验收映射和回归保护要求本身不授予编写测试的权限，例外遵循 Runtime 的明确授权边界。实际交互不可用时说明缺口，不造测试填补证据。工具执行不算人工审查，`human: not-run` 本身不产生人工审批要求。明确的用户风险接受不改变实际 failed/not-run 结果。

提升时先核对完整 delta、当前正式 owner 和真实实施证据，处理后续规则替代及直接相关 owner 的旧条款冲突；`accepted`、`merged_to` 或任务 `done` 本身不是收敛证明。然后按顺序完成：

1. 合并已验证行为，保留权限、失败、限值、兼容性及实际覆盖缺口。
2. 正式规格移除任务字段/编号/链接、change 标识/路径/来源目录及清理历史；必要依赖改为正式 owner 或直接源码，不删除 TaskAdmin 等被规定产品的真实行为。
3. 修复当前索引及受影响的既有实施计划引用；必要接受、映射和替代/移除结果写入现有规格日志，既有实施任务仅更新相关状态与证据。
4. 物理删除成功提升的 change 工作区，不搬到 archive 或创建持久副本。失败、待验证和未选择的工作区保留；全部成功且没有其他未处理内容时删除整个 `changes/` 及其路由索引。
5. 完成必要的规则、引用、消费者和格式检查后交付；若既有实施任务要求该收敛，再更新其完成状态，不为记录提升过程新建任务。

示例：“当前 changes 已通过人工审核，请按新流程提升为正式规格，移除执行关联并清理成功提升的工作区。”

直接提升独立 draft 不需要新建 change 工作区或任务。旧 `archive_state: retained` 只描述历史存储；只读检查不删除它，授权提升按当前流程核对和清理。删除中断时从剩余输入、正式 owner 和现有维护记录恢复，不为补双向引用重新创建已删除输入或任务。

规格制定完成后，交付规格和未定问题，不为关闭制定阶段实施应用或创建记录任务。实施完成后，最小必要验证和状态更新足够即交付；必需的验收或证据尚缺时，既有任务保持 review，未接受的 change 保持 draft，并说明缺口。只有计划要求的规格收敛、成功工作区删除和验证完成后，相关实施任务才能 done。当前审核不把历史 failed／partial／not-run 改成当时通过。

## 不适用场景

- 只更新 TaskAdmin 状态或 TODO；
- 普通实现任务没有行为规格需求；
- 只整理 Obsidian inbox/feedback；
- 只初始化 `.maxa/`；
- 只需要聊天中的概念解释且不落地文档。

这些场景由 TaskAdmin、Obsidian、ProjectAdmin 或普通执行流程处理。
