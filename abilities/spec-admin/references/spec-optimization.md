# Optimize Existing Specifications

Purpose: reduce the tokens an independent LLM needs to recover the same complete behavior contract. Use this workflow for an explicit request to optimize, compress or restructure existing specifications; `spec-authoring.md` owns the resulting writing style.

## Scope And Ownership

1. Resolve the requested files or directory through its spec index. A request covering all current specifications includes the formal spec documents; indexes/logs retain their routing/evidence roles and change workspaces retain their lifecycle role.
2. Inventory the full authorized set before editing. Bring each selected specification's complete current text into the executing Agent's context, including acceptance and source/coverage sections. For bounded reads, follow continuation cursors until EOF and record completion. Search/filtered views support discovery, reference checks and later diagnostics; the complete text supplies the reconstruction baseline. Preserve a local pre-edit copy and existing user changes.
3. Keep the target inventory, per-file disposition, measurements and verification in session context for delivery; do not create an optimization task. Preserve evidence in existing implementation tasks without adding reciprocal formal links.
4. Meaning-preserving optimization edits existing owners directly. Preserve behavior, lifecycle/frontmatter facts, existing temporary implementation associations and real evidence limits; formal output follows `spec-authoring.md` without execution/change associations. A discovered behavior decision follows the behavior-change workflow while the established contract remains intact.

## Contract Reconstruction

Apply `spec-authoring.md` to each target:

- From the complete source, extract each independently verifiable obligation, prerequisite, outcome, permission, precedence, exception, failure, side effect, state transition and limit. Record important unknowns as unknowns. Review cross-section duplication and shared premises before choosing the document's resulting organization.
- Reconstruct each rule from its complete fact set, including facts introduced in scenarios, data sections and acceptance text. Give every fact one normative location: a named clause, shared premise, decision table or ordered transition. Fold unique scenario outcomes into that owner; retain standalone scenarios for additional temporal/interaction information. Use the complete-rule example in `spec-authoring.md` as the representation pattern.
- Scope shared premises explicitly. Preserve distinct rollback, cancellation, partial-success and terminal-state behavior where operations differ.
- Keep stable rule identities and the consumer-required grammar/anchor subset established by reference/parser inspection. Consolidate remaining explanatory headings with their owning facts. Check actual compatibility rather than requiring the old layout to remain textually identical.
- Consolidate source citations and validation mappings by rule group. Keep acceptance and material unverified dimensions locally readable; retain detailed execution/history in its existing owner without adding task/change links to formal specs.
- Use readable standard technical language and exact interface strings. Choose syntax by measured cost and unambiguous meaning, with explicit optionality and sufficient safety/migration detail.

Build one complete replacement document from the recovered contract. Publish its whole body through a complete-file write or a prepared complete candidate followed by replacement. Preserve unchanged exact data and required identities within that candidate. Local patches serve subsequent corrections after the complete rewrite and equivalence check.

Classify every inventory entry as rewritten or retained with a concrete reason. Evaluate useful savings at the complete-document level before retaining a document: consider shared premises, repeated rule/scenario facts, evidence placement and consumer requirements together. A retained reason identifies which unique facts or actual consumer constraints account for its cost. Finish the authorized inventory as one cohesive operation.

## Validation And Measurement

- Record complete-read/EOF and whole-document replacement evidence for each rewritten target. Programmatic file reads for hashing or token counts are measurement evidence; complete source text in the executor's context establishes the reading input.
- Compare baseline and complete result by behavior group, in both directions: every original fact remains recoverable, and every resulting claim has an original basis. Check condition/actor/modality/result/permission/state/failure/exception/order/limit and retained uncertainty.
- Check governed identifiers, values, commands, errors, references and required anchors. Treat literal/number scans as supporting checks: distinguish semantic values from formatting ordinals, and document intentional equivalent representations. Accept a consolidated rule when all original facts and dependent interfaces remain recoverable; measure the new semantic organization rather than the preservation of redundant sections.
- Count complete baseline/result files with the same named tokenizer/encoding when available. Record per-file and total counts, absolute savings and percentage, including retained files. State the exact metric when only character/word counts are available. Use scope-complete totals for delivery and keep savings subordinate to contract equivalence.
- For a requested independent-reader evaluation, prepare representative boundary/precedence questions from the baseline, give a fresh reader only the resulting specs and questions, then compare answers against the original contract. Report ambiguities and the tested scope. This measures bounded comprehension, separately from source/runtime verification.
- Run affected document/link/consumer checks and whitespace validation. Existing runtime evidence remains valid for meaning-preserving edits; actual behavior changes use their own acceptance path.

If a check exposes lost or broadened behavior, restore the precise condition in its owner and rerun affected checks. If the baseline itself leaves a material question open, retain that uncertainty and report it with its scope. Preserve existing failed/partial/not-run evidence when recording the optimization result.

## Completion

Complete the inventory and required checks; add the project-required concise index/log update in its existing owner. Deliver changed/retained coverage, measured savings, semantic/reader evidence and remaining limits directly. Formal specs retain the current contract, direct source/stable dependencies and material evidence limits, not execution associations or optimization logs.
