# Telegram Bridge Maintenance Guide

## Purpose And Ownership

Maintain the shared Telegram Bot transport under `tools/telegram-bridge/` and the Neovim client under `lua/maxa/session/telegram_bridge/`. Stable current behavior is owned by `.maxa/specs/services/telegram-bridge.md` and `.maxa/specs/runtime/plugin-entrypoints.md`; proposed behavior and execution evidence live in their linked SpecAdmin change and TaskAdmin task until convergence. Read `README.md`, the changed spec rules, and the affected code before editing. Bridge is not an MCP Server.

## Session And Telegram Contract

- Persistent session identity is exact `(project_root, save_id)`, never ephemeral `chat.id`. `ask_topics` stores the session topic; `tracked_topics` retains topic identity for guarded cleanup. `notification_topics` is group-scoped fallback state, not a Chat topic. Unknown/unassociated topics never accept ordinary Chat input.
- The Bot is the sole Telegram `getUpdates` consumer. Neovim uses the authenticated local HTTP API; never poll Telegram in Lua. The configured group and owner authorize ordinary TG input. Human-assist buttons/replies use the exact request's stored destination and first-valid-result transition instead of ordinary text routing.
- Builtin `ask` and the completion listener use their exact session group topic with `ask_route: true`; legacy Bridge human-assist calls without explicit session-topic intent remain owner-private. Missing/ambiguous topic delivery never silently duplicates a builtin `ask` response privately. A known missing session topic may be recreated and recorded once before retry.
- Ordinary TG text is accepted only for a live, notify-active, idle Chat in its `ask_topics` topic. Immediately acknowledge admission as *pending submission*, not successful completion; report a later Neovim rejection separately. Reject running/offline/notify-off/unknown input immediately; do not queue it for a later turn. The Neovim submit path rechecks the exact live Chat, listener and busy state, preserves an unsent local draft, and ACKs rejected messages rather than replaying them. Local Chat input remains available. `@ask` replies and upload replies take precedence even while the agent loop runs.
- A delivered completion notice identifies that TG can reply only while the Chat remains open, notify-active and idle. A local user submission first asynchronously edits the last delivered segment, preserving its text and appending that the prior reply opportunity has ended; if delivery acknowledgment is pending, edit after it succeeds while that turn/listener generation remains current. Edit once, retain receipts only in runtime state and ignore all edit errors without warning, retry, new/private message or conversation interruption. `/v1/human-assist/notify/edit` uses authenticated exact caller identity and its cached topic; never create/recover a topic for an edit. TG-origin submissions and automatic continuations must not claim a local win. Foreground-suppressed or failed notifications do not open a reply opportunity. Suppress only when the Chat Buffer is visible in the current tab and, in tmux, a connected client displays its pane's window; no client, a hidden window, or an inspection failure/timeout sends conservatively. Foreground suppression is not a send failure. Retry only proven pre-delivery connection errors and explicit retryable rate limits/unavailability after bounded delays; do not blindly retry timeouts or ambiguous delivery, and stop retries on listener disable, Chat close or a newer completed turn.
- TG menu: `/ping`, read-only `/sessions` (live Chat running/listening state), and owner-confirmed `/clean_tracked_topics` (only known inactive session topics). Other slash commands do not become Chat input. Keep confirmation and live-state recheck before destructive cleanup; skip unknown/system topics. Neovim `:TelegramBridgePing`, `:TelegramBridgeStart`, `:TelegramBridgeStop` are service controls, not binding controls.
- A one-time Bridge schema migration drops legacy local `bindings` rows and obsolete pre-change binding/input events. Preserve Telegram topics/messages, `ask_topics`, `tracked_topics`, `notification_topics`, waiting human-assist requests and newly accepted input events across later restarts. Do not delete real TG topics to test migration.

## Configuration And Security

- Bridge defaults disabled. The service reads process/local-only environment; process variables override local files. `MAXA_ENV_FILE` selects an explicit local file. Never inspect, print, commit or paste `.env`, Bot/Bridge tokens, proxy credentials or Authorization headers. Use `just telegram-bridge-check` for redacted diagnostics; it reports only owner/group configured booleans.
- Inputs: `MAXA_TELEGRAM_BOT_TOKEN`, `MAXA_TELEGRAM_GROUP_ID` (`MAXA_TELEGRAM_CHAT_ID` is its legacy alias), `MAXA_TELEGRAM_OWNER_USER_ID`, `MAXA_TELEGRAM_BRIDGE_TOKEN`, `MAXA_TELEGRAM_SQLITE_PATH`, `MAXA_TELEGRAM_HEARTBEAT_TTL`, `MAXA_TELEGRAM_POLL_TIMEOUT`, and Bridge enabled/host/port fields. Telegram network calls use the configured proxy. Owner ID is required for human-assist replies and ordinary TG input; group ID never substitutes as owner/private destination.
- `GET /v1/health` is public. Register/heartbeat, chat-upload, human-assist, event poll/ack/result endpoints require `X-Maxa-Bridge-Token` when configured. Do not log credentials or leak topic/destination IDs to Agent-facing human-assist results. API contract changes must update affected callers and tests.

## Startup, Failures And Validation

1. Validate affected Python code with the closest Bridge tests; `just telegram-bridge-test` is the package recipe. Validate affected Lua code with the existing `nvim --headless -u NONE -l tests/util_maxa_ai_telegram_bridge_spec.lua` and `tests/util_maxa_ai_notify_telegram_state_spec.lua` where relevant. For UI interaction, use the actual Chat/TG topic rather than claiming a mocked test proves it.
2. `just telegram-bridge-restart` reloads the WSL/Linux user service; `just telegram-bridge-status` reports unit state and log path. `just telegram-bridge-log [lines]` reads `${XDG_STATE_HOME:-~/.local/state}/maxa/telegram-bridge/service.log`. If restart times out and kills only Bridge processes, verify the final service state before continuing. Compare fresh log lines after reproducing an error, not the entire historical log.
3. After changing Neovim runtime files, validate locally, then follow `mcp-creator`'s `restart_nvim_resume.lua` path; MCPHub restart alone does not reload in-process Lua. Confirm the restored Chat's local input/listener state without triggering a destructive TG cleanup.
4. `just telegram-bridge-reconcile-bot` explicitly updates the configured group's Telegram command menu and verifies `commands.matches`; it does not run on service startup. It must not drop pending updates, create topics or print secrets. A live acceptance path is: `/sessions` displays running/listening without buttons; the owner sends TG text to an idle listening Chat, then during a running turn (rejected immediately), then responds to builtin `@ask`; verify the correct nvim Chat, draft preservation and no later replay. Never use `/clean_tracked_topics` confirmation as a smoke test without explicit permission to delete topics.
5. For live failures, check group/owner authorization, `ask_topics` exact mapping, `open_chats.notify_active/running`, instance heartbeat freshness and pending-event status. Missing/stale topic errors require known-topic recovery; ambiguous delivery errors must not trigger private duplicates. If actual UI interaction is unavailable, record the attempted path, blocker and unverified behavior rather than substitute scripts or tests.
